## 一、修复本身：两行代码，一条准确的诊断链

### 改动清单

| 位置                         | 改了什么                                           |
| -------------------------- | ---------------------------------------------- |
| `MainWindow.xaml:28`       | 窗口加 `ResizeMode="NoResize"`，并配 6 行注释说明这不是审美选择  |
| `MainWindow.xaml.cs:95-98` | 构造函数里挂 `StateChanged`，非 `Normal` 立刻打回 `Normal` |

### 诊断链的技术依据

BUG 文档写的三段推理，逐条核对都对：

**① `AllowsTransparency="True"` → 分层窗口**
WPF 在 `AllowsTransparency=True` 时会给窗口加 `WS_EX_LAYERED`，用 `UpdateLayeredWindow` 提交一张 32 位带 alpha 的位图。这是"圆角透出桌面背景"的唯一做法，没有替代品。

**② 分层窗口 → 软件渲染**
这是个**硬限制**，不是配置问题。分层窗口的像素由 CPU 逐点合成后整块提交，D3D 的交换链无法直接挂上去。所以 WPF 会把这一整个窗口的 `RenderCapability.Tier` 降级到 software，`Effect`（含 `DropShadowEffect`，本来就是 GPU 像素着色器）也一起退化成 CPU 计算。

**③ 全屏 → CPU 每帧重绘 207 万像素**

```
700 × 450   =    315,000 像素
1920 × 1080 =  2,073,600 像素   ← 6.58 倍
```

而且分层窗口提交的是**整窗位图**——不是脏矩形局部更新。`_idleTimer` 每 600ms 换一次 `PetImage.Source`，每换一帧就是一次整窗重算 + 整块提交。700×450 时这是 31.5 万像素，CPU 扛得住；1920×1080 时翻 6.6 倍，渲染线程直接堵死 → 界面不再响应任何输入，看起来就是"卡死"。

**结论"不让它全屏"是对的**，而且比"优化全屏下的性能"正确得多——后者要在软件渲染上优化 207 万像素，成本高且收益为零，因为桌宠铺满整屏本身没有产品意义。

## 二、两道防线的实际强度

### 第一道：`ResizeMode="NoResize"`

`NoResize` 会移除 `WS_THICKFRAME`（可调边框）和 `WS_MAXIMIZEBOX`（最大化框）。因此：

| 路径                                     | 拦得住吗                                                                                |
| -------------------------------------- | ----------------------------------------------------------------------------------- |
| `Win+↑`                                | ✅ 拦住了——缺 `WS_MAXIMIZEBOX`，系统不响应                                                     |
| Aero Snap（拖到屏幕顶端贴顶）                    | ✅ 拦住了——而且这条路本来就是不成立的：Aero Snap 需要拖标题栏（非客户区），无边框窗口没有可拖区域，用户是自己 `DragMove()` 拖的，不经过系统 |
| 代码里 `WindowState = Maximized`          | ❌ 拦不住（`ResizeMode` 不管程序自己的赋值）                                                       |
| 第三方工具（AutoHotkey、DisplayFusion、部分显卡驱动） | ❌ 拦不住                                                                               |

所以注释里"NoResize 同时关掉最大化框和贴顶最大化"这半句**略有夸大**——贴顶那条路本来就不存在。但结论没错，多设一道没有害处。

### 第二道：`StateChanged` 兜底

```csharp
StateChanged += (s, e) =>
{
    if (WindowState != WindowState.Normal) WindowState = WindowState.Normal;
};
```

不会无限递归：第二次触发时 `WindowState` 已经是 `Normal`，条件为假。

**但它有个体验瑕疵**：这是"先让窗口变成最大化、渲染了一帧、再打回去"。用户按 `Win+↑` 时会看到窗口**闪一下**——那一帧就是 207 万像素的软件重绘，短暂但可见。

**更彻底的做法**是拦在消息层，让窗口根本不进入最大化：

```csharp
protected override void OnSourceInitialized(EventArgs e)
{
    base.OnSourceInitialized(e);
    HwndSource.FromHwnd(new WindowInteropHelper(this).Handle)?.AddHook(WndProc);
}

private IntPtr WndProc(IntPtr hwnd, int msg, IntPtr wParam, IntPtr lParam, ref bool handled)
{
    const int WM_SYSCOMMAND = 0x0112;
    const int SC_MAXIMIZE   = 0xF030;

    // wParam 低 4 位可能是系统附加标记，先屏蔽再比
    if (msg == WM_SYSCOMMAND && (wParam.ToInt32() & 0xFFF0) == SC_MAXIMIZE)
    {
        handled = true;
        return IntPtr.Zero;
    }
    return IntPtr.Zero;
}
```

对应关系：`HwndSource.AddHook` ≈ C# 桌面开发里的"原始窗口过程钩子"，就是 Win32 的 `WndProc` 子类化。`handled = true` 相当于告诉 WPF"这条消息我处理了，你别管"。

这不是必须改的，属于"从闪一下变成完全不响应"的打磨。

## 三、三道没合上的口子

### 口子一：150% 缩放已经在逼近同一个问题，只是还没到临界点

`ApplyPetScale()` 里有这段：

```csharp
Rect area = SystemParameters.WorkArea;
double fitScale = Math.Min((area.Width - 40) / BaseWidth, (area.Height - 40) / BaseHeight);
if (fitScale > 0 && scale > fitScale) scale = fitScale;
```

它的用意是"别让窗口超出屏幕"，但**客观上它用"屏幕装不装得下"在间接限制渲染面积**。而 `PetScale` 上限是 150%，两者谁先触发取决于屏幕：

| 屏幕 | WorkArea（约） | 150% 时的窗口 | 渲染像素 | 相对基准 |
|---|---|---|---|---|
| 1920×1080 | 1920×1040 | 1050×675 | 708,750 | 2.25× |
| 1366×768 | 1366×728 | 1050×675 | 708,750 | 2.25× |
| 1280×720 | 1280×680 | 995×640（被 fitScale 压到 142%） | 636,800 | 2.02× |

**在 1366×768 的笔记本上，150% 的窗口高度已经占满 93% 的可用高度。** 这不会卡死（2.25 倍还远没到 6.6 倍），但它说明：**"用比例和屏幕尺寸间接限流"这条防线上限很低**。哪天把 150% 改成 300%，或者换一块 4K 屏上有人手动改配置文件把 `PetScale` 写成 4，防线直接崩。

**建议改成显式约束**——按渲染像素数，而不是按比例：

```csharp
// 软件渲染下，像素总数就是成本本身。超过 100 万像素（约 2 倍基准）就开始压
const double MaxSoftwarePixels = 1_000_000;
if (BaseWidth * BaseHeight * scale * scale > MaxSoftwarePixels)
    scale = Math.Sqrt(MaxSoftwarePixels / (BaseWidth * BaseHeight));
```

这样约束的理由和真实成本是同一个量，而不是绕了一层。

### 口子二：`DropShadowEffect` 是常驻开销，两处

`MainWindow.xaml:52`（`ReplyBubble`）和 `:133`（`ThinkingBubble`）各挂了一个：

```xml
<DropShadowEffect Color="Black" Direction="315" ShadowDepth="3" Opacity="0.3" BlurRadius="5"/>
```

在普通窗口里这是 GPU 像素着色器，几乎免费；但在分层窗口里它退化成 CPU 高斯模糊，**并且 `LayoutTransform` 缩放时 blur 半径也跟着放大**——150% 时模糊核面积是 1.0 时的 2.25 倍。

它是 `Visibility="Collapsed"` 时不参与渲染的，所以只在气泡显示时才花钱。但气泡是桌宠的主界面，实际常驻时间不短。

**替代方案**（如果以后真觉得吃 CPU）：把阴影做成一张预渲染的九宫格 PNG 垫在边框下面，或者干脆去掉——`BorderThickness="2"` + 纯色描边已经足够把气泡和桌面区分开。

### 口子三：`SystemParameters.WorkArea` 只认主屏

`WorkArea` 返回的是**主显示器**的可用区域。用户把桌宠拖到第二块屏（常见配置：4K 主屏 + 1080p 副屏）时：

- 按 4K 算出的 `fitScale` 可能是 2.2 → 150% 直接通过
- 窗口 1050×675 拖到 1080p 副屏上，占掉 77% 宽、93% 高
- 副屏分辨率更低时，窗口甚至会超出屏幕边缘，功能栏点不回来

**修法**：用 `MonitorFromWindow` + `GetMonitorInfo` 拿窗口**当前所在显示器**的 `rcWork`，在 `LocationChanged` 里重算。这是一段 P/Invoke，成本不高但属于新知识点，按准则铁律 3 需要先跟你确认再引入。

## 四、根因还在，只是被绕开了

这次修的是**症状**（不让你进入全屏），不是**根因**（分层窗口 = 软件渲染）。这个取舍是对的，但要知道它能撑多久：

| 将来可能出现的需求 | 这次修复还够用吗 |
|---|---|
| 桌宠大小 50%~150% | ✅ 够（2.25× 以内） |
| 想让桌宠横跨两个屏幕 | ❌ 不够——那时面积是 2 倍 1080p |
| 想做"大尺寸 + 流畅待机动画" | ❌ 不够，必须换技术路线 |

真要往上走，三条路可选（都不便宜）：

1. **`WindowChrome` + 不透明窗口**：放弃真透明，用圆角裁剪 + 截图背景伪造。舍掉"透出桌面"的效果。
2. **`WS_EX_NOREDIRECTIONBITMAP` + DirectComposition**（Win8+）：能用 GPU 合成透明窗口，但要用 `CompositionTarget` 手工搭渲染树，等于绕开 WPF 的布局系统。
3. **换 WinUI 3 / Win2D**：新框架对新合成器支持好，但等于重写。

**现在的判断是对的：不为了"理论上能全屏"去付这个代价。** 记在这里，等真需要时再选。

## 五、怎么验证这步真修好了

修复是"阻止某件事发生"，最容易漏测。三步：

1. **按 `Win+↑`** —— 窗口应该不动（或闪一下回来），绝不允许卡住。
2. **把窗口拖到屏幕最顶端** —— 应该是直接被屏幕边缘挡住，不出现贴顶最大化的半透明预览框。
3. **连续按 `Win+↑` 十次** —— 确认 `StateChanged` 没有累积副作用（窗口位置、尺寸、功能栏状态都正常）。

另外建议加一行调试输出，确认兜底逻辑真的跑过：

```csharp
StateChanged += (s, e) =>
{
    if (WindowState != WindowState.Normal)
    {
        System.Diagnostics.Debug.WriteLine($"[兜底] 被拉成 {WindowState}，打回 Normal");
        WindowState = WindowState.Normal;
    }
};
```

不然你无法区分"从来没被拉成最大化"和"被拉成最大化后自己回去了"——前者说明第一道防线够用，后者说明兜底在干活。

## 六、一句话总结

**诊断链准确、修复克制、没有过度优化**——这三点做得比大多数"全屏卡死"的处理好，因为绝大多数人会选择去调 `RenderOptions.ProcessRenderMode` 或者删动画，那是治错了病。

没合上的三道口子里，只有**口子一（缩放面积会逼近临界点）**值得现在处理，改 3 行就行；另外两道可以先记着。
