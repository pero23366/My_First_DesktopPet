# 05 · 一条消息的完整旅程（前端 → 后端 → 前端）

> **记录日期**：2026-10-18 00:25
> **对应版本**：`f0e0951` 后端接入 + `0dee95f` 前后端打通
> **回答的问题**：在输入框里敲一句"今天好累"，按下回车，到小沃把回答显示出来，中间到底发生了什么？每个文件各管哪一段？

---

## 〇、先看全景

```
[浏览器]                                        [后端进程]
index.html                                      Program.cs（管道）
   ↓ 用户敲字 + 回车                                  ↑
main.js  send()                                 CORS 中间件
   ↓ 组 JSON                                       ↑
fetch() ──── OPTIONS 预检 ──────────────────────→ CORS 放行
   ↓
        ──── POST /api/chat ──────────────────→ 路由 → ChatController
                                                    ↓
                                                 ChatRequest（绑参数 + 校验）
                                                    ↓
                                                 IChatService.Reply()
                                                    ↓ RuleBasedChatService
                                                 ChatReply → JSON
   ←──── 200 + {"reply": "...", "source": "rules"} ────┘
   ↓
res.json() → data.reply → pending.textContent = 那句话
```

关键前提：**这是两个独立进程、两个端口**。

|     | 地址                      | 怎么起                    |
| --- | ----------------------- | ---------------------- |
| 前端  | `http://localhost:5173` | `npm run dev`（Vite）    |
| 后端  | `http://localhost:5003` | VS 里 F5 / `dotnet run` |

端口不同 = **不同源（origin）**。源 = 协议 + 域名 + 端口，三项里任一项不同就算跨域。
所以浏览器默认**不让** `5173` 的 JS 读 `5003` 的响应 —— 这就是 CORS 存在的理由，也是这条链上最容易卡住的地方。

## 一、阶段 1：用户敲字（`index.html` + `main.js`）

### 1.1 输入框从哪来

`index.html:46`

```html
<input class="pet__input" id="inputBox" type="text" maxlength="200" placeholder="和小鲨鱼说点什么…" />
```

- `id="inputBox"` 是 `main.js` 抓它的唯一凭据
- `maxlength="200"` 只限前端。后端 `ChatRequest` 限的是 500，两边不是同一个数 —— **前端的限制只是体验，真正的防线在后端**

### 1.2 回车是怎么变成"发送"的

`main.js:120`

```js
inputBox.addEventListener('keydown', (event) => {
  if (event.isComposing) return     // 输入法还在选词，回车是给输入法的，不是给我们的
  if (event.key === 'Enter') send()
})
```

另一个入口是 `main.js:118`：点 `#sendBtn` 也调 `send`。

> `isComposing` 这一行是 WPF 前作技术债 #3 的 Web 版修复。注意它只挡住"组合中"，
> 用回车确认候选词的那一下仍可能漏（建议再补 `event.keyCode === 229`）。

## 二、阶段 2：`send()` 做四件事（`JS/main.js`）

```js
async function send() {
  const text = inputBox.value.trim()
  if (text === '') return
  if (isSending) return

  addMessage(text, 'me')          // ① 自己说的话立刻上屏
  inputBox.value = ''             // ② 清空输入框
  scheduleAutoHide()              // ③ 起 10 秒自动隐藏计时

  const pending = addMessage('…', 'pet')  // ④ 先放一个"正在想"的占位气泡
  setBusy(true)

  try {
    pending.textContent = await postChat(text)   // ⑤ 等后端
  } catch (err) { … } finally { setBusy(false); scheduleAutoHide() }
}
```

四个设计点，各有原因：

| 做法 | 为什么 |
|---|---|
| **先上屏自己那句话**，不等后端 | 用户点了就有反应，不会以为没点上。这叫"乐观更新" |
| **先放 `…` 占位** | 后端要几十毫秒到几秒，界面不能干等着什么都不变 |
| **`isSending` 闸门 + `setBusy` 禁用按钮** | 防连按回车发同一句；顺便把"正在处理"表达出来 |
| **`finally` 里再 `scheduleAutoHide()`** | 计时从"回复到达"那一秒重新开始，而不是从"发送"那一秒 |

注意 `addMessage` 这一轮**新增了 `return li`**（`main.js:31`）—— 占位气泡的 DOM 节点被存进 `pending`，
等回复回来就直接改它的 `textContent`，不用删一个再加一个。

## 三、阶段 3：`postChat()` 发出请求（`JS/main.js:95`）

```js
async function postChat(message) {
  const controller = new AbortController()
  const timer = setTimeout(() => controller.abort(), 15000)

  try {
    const res = await fetch(getApiBase() + '/api/chat', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ message }),
      signal: controller.signal,
    })
    if (!res.ok) throw new Error('HTTP ' + res.status)
    const data = await res.json()
    return data.reply
  } finally {
    clearTimeout(timer)
  }
}
```

逐项对照：

| 代码 | 作用 | 对标 C# |
|---|---|---|
| `getApiBase()` | 从设置面板输入框取地址，空就退回 `http://localhost:5003` | 读配置文件 |
| `JSON.stringify({message})` | JS 对象 → JSON 字符串。**键名 `message` 必须和后端 C# 属性 `Message` 对上**（不区分大小写） | `JsonSerializer.Serialize` |
| `Content-Type: application/json` | 告诉后端"我发的是 JSON" | `PostAsJsonAsync` |
| `AbortController` + `setTimeout` | **`fetch` 本身没有超时**。后端挂了的话它永远不返回。这里 15 秒后主动掐断 | `CancellationTokenSource` + `CancelAfter` |
| `res.ok` | 状态码 200–299 才为 true | 检查 `IsSuccessStatusCode` |
| `await res.json()` | **第二次 await**：第一次等"响应头回来了"，第二次等"响应体读完了" | `ReadFromJsonAsync` |

> 两次 `await` 是很多人第一次接后端时最容易懵的点：`fetch` resolve 的时候，
> body 可能还没到，所以 `res.json()` 又是一个 Promise。

## 四、阶段 4：跨过那道墙（CORS 预检）

因为 `Content-Type: application/json` 不属于浏览器的"简单请求"，所以真正那个 POST **之前**，
浏览器会自己先发一个：

```
OPTIONS /api/chat
Origin: http://localhost:5173
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type
```

这个预检**不经过你的任何 C# 代码**，由 `Program.cs` 里注册的 CORS 中间件直接应答：

```csharp
policy.WithOrigins(
    "http://localhost:5173", "http://127.0.0.1:5173",  // Vite dev
    "http://localhost:4173", "http://127.0.0.1:4173",  // Vite preview
    "http://localhost:5500", "http://127.0.0.1:5500")  // Live Server
  .AllowAnyHeader()
  .AllowAnyMethod();
```

- 源在白名单里 → 回 `Access-Control-Allow-Origin: http://localhost:5173`，浏览器放行，才发真正的 POST
- 源不在白名单 → 预检失败，**前端只会看到一句笼统的 "Failed to fetch"**，控制台里一条 CORS 报错 —— 这是排查时第一要看的地方

还有一处顺序死规定（`Program.cs:54`）：

```csharp
app.UseCors(CorsPolicy);   // 必须在 MapControllers 之前
app.UseAuthorization();
app.MapControllers();
```

`UseCors` 排在 `MapControllers` 后面的话，预检请求走不到 CORS 中间件，响应里就没有 `Allow-Origin` 头。

## 五、阶段 5：请求进后端，按顺序过管道（`Program.cs`）

`Program.cs` 其实分两段，很多人会看混：

| 段 | 代码块 | 什么时候执行 |
|---|---|---|
| **服务注册** | `builder.Services.Add…` | 进程**启动时执行一次**，往 DI 容器里放东西 |
| **请求管道** | `app.Use…` / `app.Map…` | **每个请求进来时按顺序走一遍** |

请求进来后的顺序：

```
请求 → [CORS 中间件] → [授权中间件] → [路由匹配] → ChatController.Post() → 你的代码
```

这个文件里跟"这一句话"直接相关的只有三样：

1. `AddControllers()` —— 让框架认识 `[ApiController]` 标记的类
2. `AddSingleton<IChatService, RuleBasedChatService>()` —— 告诉 DI："有人要 `IChatService`，就给他 `RuleBasedChatService`"
3. `AddCors(...)` + `UseCors(...)` —— 放行前端那个源

## 六、阶段 6：控制器接住（`Controllers/ChatController.cs`）

```csharp
[ApiController]
[Route("api/chat")]
public class ChatController : ControllerBase
{
    private readonly IChatService _chat;
    public ChatController(IChatService chat) => _chat = chat;

    [HttpPost]
    public ActionResult<ChatReply> Post([FromBody] ChatRequest request) { … }
}
```

按发生顺序拆：

| 步骤 | 谁做的 | 说明 |
|---|---|---|
| ① 路由匹配 | `[Route("api/chat")]` + `[HttpPost]` | URL 是 `/api/chat` 且方法是 POST，才进这个方法 |
| ② 模型绑定 | `[FromBody] ChatRequest request` | 把请求体的 JSON **反序列化**成 C# 对象 |
| ③ 自动校验 | `[ApiController]` + `ChatRequest` 上的数据注解 | 不合法就**自动返回 400**，根本进不到方法体 |
| ④ 拿实例 | 构造函数注入 | DI 把 `RuleBasedChatService` 塞进 `_chat` |
| ⑤ 干活 | `_chat.Reply(text)` | 交给服务层 |
| ⑥ 包装返回 | `Ok(new ChatReply{…})` | 变成 `200 + JSON` |

`[ApiController]` 这三个字值很多钱 —— 它把"参数为空/超长就返回 400"这件苦活全包了。
方法体里那个 `if (text.Length == 0)` 是**第二层**防御，注释里也写明了理由。

## 七、阶段 7：入参与出参（`Models/`）

### `Models/ChatRequest.cs` —— 进来的形状

```csharp
public class ChatRequest
{
    [Required(ErrorMessage = "message 不能为空")]
    [StringLength(500, MinimumLength = 1, ErrorMessage = "message 长度要在 1~500 之间")]
    public string Message { get; set; } = "";
}
```

- `Message` 对应前端 `{ "message": "…" }`（JSON 绑定不区分大小写）
- `[Required]` 默认不允许空字符串
- 校验不通过 → 自动 400，响应体是 `ProblemDetails`（含字段级错误信息）

### `Models/ChatReply.cs` —— 出去的形状

```csharp
public class ChatReply
{
    public string Reply { get; set; } = "";              // → 前端 data.reply
    public string Source { get; set; } = "rules";        // → data.source
    public DateTimeOffset ReceivedAt { get; set; }       // → data.receivedAt
}
```

**`Reply` → `reply` 这个大小写变化是自动的**：ASP.NET 默认用 `System.Text.Json` 的 camelCase 策略。
所以 C# 里写大驼峰是惯例，前端收小驼峰也是惯例，两边不用手动对齐 —— 但要知道**是谁在中间翻的**。

## 八、阶段 8：谁在决定说什么（`Services/`）

### `Services/IChatService.cs` —— 一份契约

```csharp
public interface IChatService
{
    string Reply(string message);
}
```

### `Services/RuleBasedChatService.cs` —— 现在的实现

```csharp
private static readonly (string[] Keywords, string[] Replies)[] Rules = [ … ];

public string Reply(string message)
{
    foreach (var (keywords, replies) in Rules)
        foreach (var keyword in keywords)
            if (text.Contains(keyword, StringComparison.OrdinalIgnoreCase))
                return replies[text.Length % replies.Length];

    return Fallbacks[text.Length % Fallbacks.Length];
}
```

| 设计 | 为什么 |
|---|---|
| **用接口框起来** | 以后接 DeepSeek，只要再写一个 `LlmChatService : IChatService`，改 `Program.cs` 一行注册，控制器一行不动 |
| **注册成 `Singleton`** | 无状态、无 per-request 数据，一个实例够用，也最省内存 |
| **规则用数组不用 if-else 链** | 加规则只改数据，不改逻辑 |
| **`text.Length % replies.Length` 而不是 `Random`** | 同一句话永远得到同一个回答 —— 出问题时能复现 |

"今天好累" 这句话会发生什么：命中 `["累", …]` 那组规则 → 取 `replies[4 % 3]` = 第 2 句。

## 九、阶段 9：回到前端（`JS/main.js` 收尾）

```
后端 200 + {"reply":"那就先停一下。停不是输。","source":"rules","receivedAt":"..."}
   ↓ res.ok → true
   ↓ await res.json() → { reply, source, receivedAt }
   ↓ return data.reply
   ↓ pending.textContent = "那就先停一下。停不是输。"
   ↓ finally: setBusy(false) + scheduleAutoHide()
```

于是输入框解锁、焦点回来、那个 `…` 换成了真话、气泡重新开始 10 秒倒计时。

失败分支：

| 情况              | `err.name`   | 用户看到                     |
| --------------- | ------------ | ------------------------ |
| 15 秒没回来，被自己掐断   | `AbortError` | 「（想太久了……先不说这个）」          |
| 后端没起 / CORS 不放行 | `TypeError`  | 「（我连不上后端，去设置里看看 API 地址）」 |

## 十一、这条链上现在还有的坑

| # | 位置 | 问题 |
|---|---|---|
| 1 | `index.html:68` | 输入框 `placeholder="http://localhost:5080"`，但实际默认是 **5003**。占位文案在骗人，改成 5003 |

## 十二、总结

一句话概括整条链：

> **`main.js` 把一句话变成 JSON 发出去，`Program.cs` 的 CORS 先放行、路由再把请求交给 `ChatController`，控制器把 JSON 变回 C# 对象并校验，然后问 `IChatService` 要答案，最后把答案包装成 JSON 原路返回，`main.js` 把那个 `…` 就地换成真话。**

这条链上有**三个"看不见的翻墙点"**，也是新手最容易懵的三处：

1. **CORS 预检** —— 你看不到的那个 `OPTIONS` 请求，它失败时前端只给一句 "Failed to fetch"
2. **camelCase 转换** —— C# 的 `Reply` 到前端变成 `reply`，中间是 `System.Text.Json` 在翻
3. **两次 `await`** —— `fetch` 一次等响应头，`res.json()` 再一次等响应体

以及**一个架构上的收获**：`IChatService` 这个接口，让"小沃怎么说话"和"怎么接 HTTP 请求"彻底解耦了。
下一步接 DeepSeek，只需要写一个新的实现类 + 改 `Program.cs` 一行，`ChatController` 一个字都不用动 ——
这就是你 .NET 那边学了 63 篇的依赖注入，在真实项目里第一次真正省到钱的地方。
