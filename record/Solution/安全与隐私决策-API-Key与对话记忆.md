# 安全与隐私决策记录：API Key 的归属与对话记忆的存储

> **记录时间**：2026-10-18 22:00 ~ 22:30
> **触发场景**：桌面宠物「小沃」从「本机自用」转向「公开发布」，需要接入真正的大模型 API
> **参与讨论的两条硬约束**：① 成本由用户承担；② API Key 绝不能泄露
> **最终结论**：采用 **A 方案（浏览器直连厂商）+ 本地记忆（IndexedDB）**，后端只下发人设 prompt，不接触 key、不接触对话内容

---

## 一、问题起因

### 1.1 项目定位变了，问题才出现

V1 阶段的小沃是一个**跑在自己电脑上**的网页：后端是本机 ASP.NET Core（`localhost:5003`），回复来自 `RuleBasedChatService` 的关键词规则表，一分钱不花，也没有任何秘密可泄。

转向 cyberpet 之后，目标变成「发布出去让所有人访问」。这两件事一旦同时成立，三个新问题立刻冒出来：

1. **谁付钱**：真接大模型，每次对话都在烧钱，学生党没有收入
2. **key 放哪**：调用大模型必须有 API Key，而这个 key 等于钱包
3. **记忆放哪**：桌宠要有情感就得记得住用户，可「记得住」意味着「存东西」，存东西就意味着「别人能看到」

### 1.2 最初的关键误解：以为 JSON 能加密

讨论开头提出的假设是：

> 「千万不能暴露 APIKEYS（我记得可以通过 JSON 来实现加密的吧？？）」

这个误解必须记下来，因为它是这件事里最容易踩、最贵的一个坑：

- **JSON 是数据格式，不是加密手段。** 把 key 写成 `{"apiKey":"sk-xxx"}` 放前端，打开 F12 → Network 面板，明文完整可见
- **Base64 是编码，不是加密。** `atob()` 一行就能还原
- **真正的加密必须有「密钥」。** 如果解密用的密钥也在浏览器里，那它就不是秘密

一句话原则：**只要浏览器拿到过 key，key 就已经泄露了。** 这件事靠「编码/混淆」无法补救，只能靠「不让它到浏览器」。

### 1.3 由此产生的具体担忧（用户原话整理）

| # | 担忧 | 本质 |
|---|---|---|
| 1 | 能不能让用户自己填 key | 成本转嫁的可行性 |
| 2 | 「所有的密钥在我的手上」怎么办 | 我成了 key 的保管人，责任与风险都在我 |
| 3 | 有没有专门的云端托管 | 有没有「平台代管」的现成产品 |
| 4 | 大一，没有很多钱 | 零预算约束 |
| 5 | 感觉 Web 发布比桌面开发麻烦多了 | 对第一次部署的畏难 |
| 6 | 对话要记住（情感），但我不想看大家的消息 | **功能与隐私的冲突** |
| 7 | 关窗口时能把上下文存到后端吗 | 持久化时机 |
| 8 | 后端数据库有限，总不能全放我电脑上；20G 够吗 | 容量与部署形态 |

### 1.4 必须先承认的一个事实

> 「我们现在这段对话，是不是都上传到后端了？」

**是。** 每条消息必须送到模型所在的服务器才能生成回复，这是推理的物理前提，没有例外。所谓「AI 对话不上传」只有两种可能：模型跑在本地（要显卡），或者根本没在用 AI。

所谓安全，靠的是三样，且都不是魔法：

1. **TLS**：传输链路是密文，路上抓包看不到内容
2. **服务商数据政策**：是否用于训练、留存多久 —— 这是**承诺**，不是技术保证
3. **权限隔离**：只有持账号凭据的人能调取历史

**结论：服务商理论上能看到你的聊天。** 所有「安全」的说法，都是在这个前提下的工程折中。这一点想明白，后面所有方案的好坏判断才有基准。

## 二、解决过程（含抉择过程）

整个过程走了六轮，每轮都在回答一个更精确的问题。

### 第 1 轮：先把「密钥能不能放前端」钉死

- 结论：**不能。** 理由见 §1.2
- 由此确定一条不可动摇的底线：**key 只在服务端，或只在用户自己的浏览器里，绝不经过「我」这个中间人**

### 第 2 轮：追问「那后端还有什么用？」

这是一个很好的质疑 —— 如果 key 不放后端、对话也不存后端，那 ASP.NET Core 这一坨是不是白写了？

梳理出后端在接真 API 后的五项真实价值：

1. **藏 key**（当 key 由站长持有时）
2. **统一改模型与人设**：换供应商、调 prompt 只改后端一处，前端不动
3. **存数据**：历史、语料、将来的检索库
4. **限流与配额**：防止有人按住回车刷爆余额
5. **绕浏览器限制**：第三方 API 常不开放 CORS；各家 SDK 也是为服务端设计的

**关键认识**：这五条里，只有 1、4 依赖「后端持 key」。如果 key 在用户手里，2、3、5 依然成立，1、4 则自动失效（因为花的不是站长的钱，也不需要防刷）。

### 第 3 轮：盘点「用户自己出 key」的三条实现路线

| 方案 | 谁付钱 | key 是否经过我的服务器 | 代价 |
|---|---|---|---|
| **A. 浏览器直连（BYOK）** | 用户自己的 key | **完全不经过** | 后端拿不到对话；历史只能存浏览器；要求厂商开 CORS |
| **B. 额度制（站长代付）** | 用户买站长的额度/兑换码 | 只有站长 1 个主 key，永不出服务器 | 需要收款渠道 + 防滥用 |
| **C. 服务端转发 BYOK** | 用户自己的 key | 一次性经过（不落盘、不打日志） | 用户必须信任站长 |

**抉择要点：**

- C 是最常见的小站做法，但它只能给出「我承诺不看」的**承诺级安全**，给不出**结构级安全**。而用户明确说「所有的密钥在我的手上」，说明他介意的恰恰是这一点 —— 所以 C 出局
- B 的安全性最好（key 结构上不出服务器），但需要收款流程，且大一没有收入、也没有支付资质，短期内不现实
- **A 同时满足「成本用户承担」和「key 不泄露」，且零成本启动**，唯一代价是后端看不到对话

### 第 4 轮：查证「有没有更专业的云端方案」

结论：**有，但不适用于聊天场景。**

- 业界确实有标准做法：服务端持长期 key → 签发**几十秒过期的临时 token** → 浏览器拿短命 token 调厂商（Gemini Live ephemeral token、OpenAI Realtime ephemeral key）
- 但这类机制是给**实时语音/多模态接口**设计的；**普通 chat completions 没有这种机制**
- 商业化产品里，「云端密钥服务」（AWS KMS / Azure Key Vault / Cloudflare Secrets）解决的是「企业管自己的 key」，**不解决「替陌生用户保管 key」**

同时查证了零成本起步的现实选项（政策会变，用前以官网为准）：

- **Gemini**：3.5 Flash-Lite 有免费层，日常几句完全够
- **OpenRouter**：提供 `:free` 后缀的免费模型
- **Cloudflare Workers AI**：有免费额度
- **GitHub Student Pack**：学生认证后含 Azure / DigitalOcean 额度，可换一台 VPS

顺带校准了成本预期（**2026-08 大幅调价后**，别按旧印象估算）：

| DeepSeek V4-Pro | 输入（缓存未命中） | 输出 |
|---|---|---|
| 高峰（工作日 9-12、14-18） | 9 元 / 百万 token | 27 元 / 百万 token |
| 低谷（其余时间 + 周末全天） | 4.5 元 / 百万 token | 13.5 元 / 百万 token |

按小沃一句回复约「200 输入 + 100 输出」估算：**一句约 0.2~0.5 分钱，1000 句约 2~5 元。** 真正烧钱的不是「人多」，而是「有人狂刷」，所以要防的是滥用而不是用户量。

### 第 5 轮：把「记忆」和「隐私」拆开

用户的需求是复合的：「要记住、要有情感」+「我不想看大家的消息」。拆解后发现「记忆」根本不是一件事，而是三层：

| 记忆类型 | 是什么 | 存哪 | 成本 |
|---|---|---|---|
| **长期人设** | 小沃说话短、有点丧但温柔 | 不用存，就是后端一段 system prompt | 0 |
| **近期上下文** | 刚才聊了啥，用来接话 | 浏览器本地 | 0 |
| **长期记忆点** | 「用户说过他在学前端」 | 会话结束时让模型总结 2~3 条 | 很小 |

**判断**：前两层就足以让桌宠「有情感」了，而且完全在用户自己电脑上 —— 站长零成本、零隐私责任。第三层才涉及跨设备。

### 第 6 轮：关窗保存、数据库容量、部署形态

**（a）关窗时保存上下文：能做，但关键不在「怎么存」**

- 技术手段：`visibilitychange` / `pagehide` + `navigator.sendBeacon()`
  （普通 `fetch` 在页面关闭时会被浏览器掐断，`sendBeacon` 是唯一可靠的方式）
- 但真正的问题是**存明文还是密文**：

| 存法 | 站长能看到吗 | 跨设备 | 复杂度 |
|---|---|---|---|
| 浏览器本地 IndexedDB | 看不到 | ❌ | 低 |
| 后端存明文 | **能看到**（只是不看） | ✅ | 低 |
| 后端存密文（端到端加密） | 看不到 | ✅ | 中高 |

- 第三种才是「跨设备 + 绝对看不到」的正解：浏览器用口令派生密钥加密，上传的只有密文，后端连解密能力都没有
- **但大一项目不需要一步到位**：本地存储能满足 90% 的需求，且连数据库都不用建

**（b）容量：20G 是严重过剩，焦虑错了地方**

| 项 | 估算 |
|---|---|
| 中文 1 字（UTF-8） | 约 3 字节 |
| 一条 100 字消息 | 约 300 字节 |
| 一次 20 条会话（含元数据） | 约 5~10 KB |
| 1 万次会话 | 约 100 MB |
| 10 万次会话 | 约 1 GB |
| **20 GB** | **约 200 万次会话** |

**结论：磁盘永远不是瓶颈。**

**（c）真正的瓶颈是「别把服务跑在自己家电脑上」**

1. 家用宽带无固定公网 IP，80/443 常被封
2. 机器一关服务就挂，在线率不可控
3. **公网暴露 + 无人运维 = 安全风险**（扫端口、弱口令、未打补丁，一晚上就能被拖库）

正解是放到免费云：**Cloudflare Pages + D1**、**Supabase 免费 500MB**、或 **Student Pack 换的 VPS**。

### 2.7 被否掉的方案清单（及原因）

| 被否方案 | 否掉的原因 |
|---|---|
| key 写在前端 JSON / Base64 | 不是加密，F12 即明文 |
| key 存 `localStorage` 明文 | 任何 XSS 或恶意扩展可读；且长期驻留 |
| 服务端转发 BYOK（C） | 只能给「承诺级」安全，用户明确介意这一点 |
| 服务端明文存对话 | 「我看不到」变成一句空话，与需求 3 冲突 |
| 依赖第三方 API 中转站 | 等于把 key 交给另一个陌生人，风险叠加 |
| 把后端跑在家用电脑上对外 | 安全、在线率、运维三方面都不可控 |
| 一步到位做端到端加密云备份 | 复杂度高，当前无跨设备刚需，属于过度设计 |

### 2.8 贯穿全程的三个判断原则

1. **把「成本 / 密钥 / 记忆」三件事拆开谈**。混在一起会觉得无解，拆开后每件都有明确解法
2. **区分「承诺级安全」和「结构级安全」**。前者靠人品和文档，后者靠「我根本拿不到」
3. **先满足 90%，把剩下的 10% 留到有人抱怨时再做**

## 三、最终方案

### 3.1 一句话

**A 方案（浏览器直连厂商）+ 本地记忆（IndexedDB）+ 后端只下发人设。**

### 3.2 数据流

```
用户输入
   │
   ▼
浏览器（持有用户自己的 key，仅存 sessionStorage / 内存）
   │  ── 直接 HTTPS ──▶  模型厂商（OpenAI 兼容接口 / Gemini）
   │                        │
   │  ◀────── 回复 ─────────┘
   ▼
渲染气泡 + 写入 IndexedDB（只在本机）

另一个方向：
浏览器 ── GET /api/persona ──▶ 我的 ASP.NET Core（只回人设 prompt，无 key、无对话）
```

**关键点：中间那条竖线完全不存在。** 我的后端不在「用户 → 厂商」这条路径上，所以：

- 没有 key 可泄露
- 没有对话内容可看
- 没有滥用需要防（刷的是用户自己的钱）

### 3.3 API Key 的处理

| 环节 | 做法 |
|---|---|
| 存储位置 | 只放 `sessionStorage` 或仅内存变量，**不写 `localStorage`、不写 cookie、不写磁盘** |
| 输入框 | `type="password"` + `autocomplete="off"` |
| 回显 | 只显示掩码 `sk-…a1b2`，永不回显完整值 |
| 清除 | 提供「清除 key」按钮；关页面自动失效 |
| 传输 | 只发给厂商域名，不发给本站后端 |
| 页面安全 | 不引任何第三方脚本/CDN，降低 XSS 面 |
| 日志 | 前端 `console` 不打印 key；生产环境不留调试输出 |

### 3.4 记忆的处理

- **人设**：固定 system prompt，由后端 `GET /api/persona` 下发（不含任何秘密）。改人设只改后端一处
- **近期上下文**：IndexedDB 存最近 N 轮（建议 10~20 轮），每轮 `{role, content, ts}`；超出截断
- **长期记忆点**：会话结束时调一次模型，产出 2~3 条摘要（如「用户在学前端」），单独存一个 store
- **容量控制**：IndexedDB 有配额，超过就按时间淘汰最旧的会话，保留摘要

### 3.5 后端保留的职责（没有被废掉）

1. 托管前端静态资源（生产环境）
2. 下发人设 prompt（`/api/persona`），保持「改人设只改一处」
3. 未来 B 方案的入口：额度、配额、鉴权
4. 未来 E2E 云备份的入口：只存密文

### 3.6 验收清单（发布前逐条自查）

- [ ] F12 → Application → 无任何 cookie / localStorage 里存有 key
- [ ] F12 → Network → 本站域名下没有任何请求带 `Authorization` 或 key 参数
- [ ] 关闭页面后重开，key 已失效（需重填）
- [ ] 页面不加载任何第三方脚本
- [ ] 全站 HTTPS
- [ ] `git log` 与仓库内无任何 key 痕迹（包括历史提交）
- [ ] 明确告知用户：key 只存在你自己浏览器里，我们不保存也看不到

### 3.7 未来升级路径（按触发条件，不提前做）

| 触发条件 | 升级动作 |
|---|---|
| 用户抱怨「换设备就不认识我了」 | 上端到端加密云备份（密文上传，后端无解密能力） |
| 出现愿意付费的陌生用户 | 上 B 方案：站长主 key + 额度制 + 兑换码 |
| 要做实时语音 | 接厂商的 ephemeral token 机制（短命 token） |
| 用户量真的起来了 | 迁到 Cloudflare D1 / Supabase，别再自托管 |

### 3.8 已知残留风险（诚实清单）

1. **Key 在浏览器内存里**：XSS 或恶意扩展理论上可读。缓解：不引第三方脚本、sessionStorage 而非 localStorage
2. **厂商能看到对话**：这是推理的物理前提，只能靠服务商政策约束
3. **换设备/清缓存后记忆丢失**：本地存储的必然代价，用 §3.7 的 E2E 备份解决
4. **用户可能拿到的是别人的 key**（共享 key 场景）：不是安全问题，但会互相消耗额度，需要在文案里提示
5. **免费额度政策会变**：各家的免费层随时可能收紧，不要把产品架构押在「永久免费」上

## 五、一句话总结

> **最强的隐私保护不是"我保证不看"，而是"我根本拿不到"。**
> A 方案之所以是对的选择，不是因为它省钱，而是因为它把「信任问题」变成了「结构问题」——
> 用户的 key 和对话，从来没有出现在我的服务器上。
