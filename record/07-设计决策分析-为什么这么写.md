## 〇、先把总取向说清楚

这份代码不是随手写的，它一直在守三条线：

| 主线 | 具体表现 | 一句话 |
|---|---|---|
| **出口唯一** | 渲染只走 `addMessage`，地址只走 `getApiBase` | 同一件事只有一个地方做，改需求只改一处 |
| **失败显式** | `res.ok` 手动判断、`catch` 分两支、`console.error` 不吞 | 宁可多写几行，不让错误悄悄消失 |
| **状态最少** | 只有 `isSending` 和 `hideTimer` 两个模块级状态 | 状态越少，越不容易和视图打架 |

下面所有的"为什么"，都是这三条线推出来的。

## 一、选型层：三个大方向

### 1.1 不上框架，直接操作 DOM

| | |
|---|---|
| **替代方案** | React / Vue 的声明式渲染；或者 jQuery 式的链式操作 |
| **为什么选这个** | 准则铁律 1：**核心目的是练 JS**。页面上总共 12 个节点，手写的成本远低于"学框架 + 配构建"的成本 |
| **直接好处** | 没有虚拟 DOM、没有响应式追踪，`querySelector` 拿到什么就是什么，调试时 F12 看到的就是真相 |
| **代价（重要）** | **视图和状态靠人脑同步。** 06 里那个"气泡被自动藏起来、回复回来只改了文字"的 bug，本质就是：状态（`textContent`）变了，视图的另一半（`hidden` 类）没人去改。React 那类框架正是靠"状态一变就整体重算"来消灭这类 bug |
| **什么时候该换** | 元素超过 50 个、或者有 5 个以上互相影响的状态时。本项目的"聊天记录 + 设置面板 + 待机动画"还远没到 |

> 这不是"框架不好"，是**此刻学框架会稀释 JS 练习**。等 V1 跑通，这一堆手工同步的痛点会成为学框架最好的动机。

### 1.2 `type="module"` 而不是 IIFE / 全局函数

| | |
|---|---|
| **替代方案** | `(function(){ … })()` 立即执行函数；或者直接写全局变量 |
| **为什么选这个** | ① 自动 `defer`，脚本在 HTML 解析完才跑 → **不用写 `DOMContentLoaded`**；② 模块有自己的作用域，12 个 `const` 不会挂到 `window` 上；③ 将来拆文件能直接 `import/export` |
| **代价** | 必须通过 http 打开（`file://` 会被模块的 CORS 规则拦死）→ 这也是必须要 Vite 的原因之一 |

### 1.3 12 个节点一次性抓齐，而不是随用随查

```js
const inputBox = document.querySelector('#inputBox')
// 后面全程用 inputBox，不再 document.querySelector
```

| | |
|---|---|
| **替代 A** | 每次用的时候现查：`document.querySelector('#inputBox').value` |
| **替代 B** | 事件委托：所有点击挂到 `body` 上，靠 `e.target` 分辨 |
| **为什么选这个** | ① 查一次省一次 DOM 遍历；② 名字化之后代码是自解释的；③ **启动即暴露错误** —— id 打错的话第一行就 `null`，而不是等用户点到那个按钮才崩 |
| **代价** | **缓存的引用只在"节点不被重建"时有效**。如果哪天用 `innerHTML` 重建了整块 HTML，之前存的变量全部指向已经不在文档里的旧节点 —— 改它没反应，也不会报错（最阴的一类 bug） |
| **判断依据** | 这批节点是 HTML 里静态写死的，生命周期比代码长 → 缓存安全。**如果是动态生成的列表项，就绝不能缓存** |

## 二、DOM 层：五个小决定，每个都在防一种事故

### 2.1 `textContent` 而不是 `innerHTML`

| | |
|---|---|
| **换算** | `li.innerHTML = text` 只需改一个词 |
| **为什么不能这么写** | 用户输入 `"<img src=x onerror=alert(1)>"` 时，`innerHTML` 会**真的把它当标签插进 DOM 并执行**。这就是 XSS 最经典的一条路，而且受害者是下一个打开这个聊天记录的人 |
| **好处** | 天然免疫；还更快（不跑 HTML 解析器） |
| **代价** | 不能塞富文本。真要加粗就得 `createElement('b')` 分段拼，麻烦但安全 |
| **一句话** | **凡是"用户能控制的内容"，永远走 `textContent`** |

### 2.2 `addMessage` 作为唯一渲染出口

| | |
|---|---|
| **替代** | 每个需要加消息的地方自己 `createElement` + `append`（现在有 4 处会调它） |
| **好处** | 现在加时间戳、加头像、加"发送失败重发"按钮，**只改一个函数**。而且"滚到底""叫醒气泡"这两步不会漏 |
| **代价** | `from` 参数成了隐式协议（只能传 `'me'` / `'pet'`），传错不会报错、只是样式丢失。更稳的是 `li.classList.add('pet__msg', 'pet__msg--' + from)` 或干脆用两个函数 `addMyMessage` / `addPetMessage` |
| **本质** | 这是"单一出口"原则的最小实现 —— 一个函数，替代 N 处重复 |

### 2.3 `return li` 而不是"删一个再加一个"

| | |
|---|---|
| **替代** | 回复到了先 `pendingLi.remove()`，再 `addMessage(reply,'pet')` |
| **好处** | 少一次 DOM 增删 → 少一次重排；**滚动位置不跳**（删了再加，滚动条会闪一下）；占位和结果是同一个节点，"正在想"到"说完了"是平滑过渡 |
| **代价** | 调用方必须持有引用（`const pending = …`），节点生命周期被拉长一点 |

### 2.4 `classList` 而不是 `style.display` / `className +=`

| 写法 | 问题 |
|---|---|
| `el.style.display = 'none'` | 写成**内联样式**，优先级最高。将来 CSS 里想让某个断点下强制显示，得用 `!important` 才压得住 |
| `el.className += ' hidden'` | 字符串拼接，重复调用会叠出 `"hidden hidden"`；而且一不小心把 `pet__msg` 这种基础类冲掉，消息就没样式了 |
| `el.classList.add/remove/toggle` | ✅ 幂等、只管一个类、不碰别的类名 |

**代价**：`.hidden` 用了 `display:none !important`，因为 `.pet` 和 `.pet__settings` 显式写了 `display:flex` 且定义在后面。
换成 `.pet.hidden { display:none }` 这种双类选择器也能不用 `!important`，但项目里元素一多就要为每个组件写一遍。
**`!important` 在这里是"用一个集中开关换掉 N 个分散规则"，是划算的。**

### 2.5 用 `.hidden` 类而不是 `<dialog>` / 原生 `hidden` 属性

| | |
|---|---|
| **原生 `hidden` 属性** | 浏览器默认样式就是 `display:none`，但它会被组件的 `display:flex` 覆盖（优先级更低），而且语义是"暂时不相关"，不适合"切换视图" |
| **`<dialog>`** | 自带遮罩和焦点管理，但它是**模态**语义，会锁住页面其余部分 —— 聊天窗口不该这样 |
| **类切换** | 最朴素，也最容易加过渡动画（将来淡入淡出只需给 `.pet` 加 `transition: opacity`） |

## 三、交互层：四个决定，都在处理"等待"和"重复"

### 3.1 乐观更新 + 占位（本文件最核心的设计）

```js
addMessage(text, 'me')              // 自己的话立刻上屏
const pending = addMessage('…', 'pet')  // 先放一个"正在想"
pending.textContent = await postChat(text)  // 回来就地替换
```

| | |
|---|---|
| **替代 A** | 等回复回来，两条一起渲染 → 从点击到显示可能空白 2~5 秒，用户会以为没点上，反复点 |
| **替代 B** | 全屏 loading 遮罩 → 太重。聊天场景的等待是"局部"的，不该锁住整个界面 |
| **好处** | 感知延迟 ≈ 0；**失败也能就地显示** —— 占位气泡直接变成错误文案，不需要"回滚"自己那条消息 |
| **代价（这次真的付了）** | **乐观更新真正的成本不在"放占位"，在"兜住等待期间所有异步事件"。** 等待期间那个 10 秒自动隐藏会先把气泡藏起来，而回复回来只改文字、不叫醒气泡 → 回复永远看不见（06 第①个 bug）。**框架的价值之一就是替你兜住这类事** |

### 3.2 `isSending` + `disabled` 两把锁一起上

| 只上一把 | 漏在哪 |
|---|---|
| 只有 `isSending` | 按钮看起来还能点，用户会困惑"为什么没反应" |
| 只有 `disabled` | **回车路径不经过按钮**，照样能重复发 |

**代价**：状态存了两份（JS 变量一份、DOM 属性一份），理论上可能不同步。
但 `setBusy()` 是唯一写入口，两份永远一起变 —— 这就是"单一写入口"的价值。

### 3.3 直接传函数名 `addEventListener('click', send)`

| | |
|---|---|
| **替代** | `addEventListener('click', () => send())` |
| **好处** | ① 少一层闭包；② **将来能删掉** —— `removeEventListener` 要求传"同一个函数引用"，而箭头函数每执行一次都是新的对象，删不掉 |
| **代价** | 拿不到 `event` 对象（这里不需要；`keydown` 那个就需要，所以那边写了箭头函数） |

### 3.4 可撤销的定时器：存 ID + 先清再设

```js
let hideTimer = null
function scheduleAutoHide() {
  clearTimeout(hideTimer)   // 先撤销
  if (!autoHideToggle.checked) return
  hideTimer = setTimeout(…, 10000)  // 再设新的
}
```

| | |
|---|---|
| **不存 ID 的后果** | 连发 3 条消息 → 3 个倒计时同时在跑 → 第一个到时气泡就没了，用户还有 2 条没看完 |
| **好处** | 实现"重置"语义：任何新消息都把 10 秒从头算 |
| **命名** | 叫 `scheduleAutoHide`（安排隐藏）而不是 `hide`（隐藏），因为它不是立即执行。**命名准确 = 少一次误读** |

## 四、通信层：五个决定，全在补 `fetch` 的默认坑

### 4.1 `async/await` 而不是 `.then` 链

```js
try {
  const res = await fetch(...)
  if (!res.ok) throw ...
  const data = await res.json()
  return data.reply
} catch (err) { ... } finally { ... }
```

| | |
|---|---|
| **`.then` 版本** | `fetch(url).then(res => res.json()).then(data => data.reply).catch(...)` |
| **为什么用 await** | ① 错误**就地**捕获：`catch` 能接住 `fetch` 和 `res.json()` 两处的失败，`.then` 链里中间任何一环失败都会直接穿到链尾，不知道死在哪一步；② `try/catch/finally` 和 C# 长得一模一样；③ 能写普通的 `if / return`，不用在回调里嵌套 |
| **代价** | `async` 函数返回 Promise。当事件回调用时，若内部抛错且没 catch，会变成 unhandled rejection（静默失败）。所以 `send()` 和测试连接的 `async` 回调都必须自带 `try/catch` |

### 4.2 `AbortController` 而不是 `Promise.race` 超时

| 方案 | 行为 | 问题 |
|---|---|---|
| `Promise.race([fetch, timeout])` | 只是"代码不再等了" | **请求还在发**，后端照样处理，连接不释放，浏览器还在占资源 |
| `AbortController` | 真的掐断请求 | ✅ 浏览器主动断开连接，后端也能感知到客户端走了 |
| 只靠后端超时 | 防"后端卡死" | 防不了"根本没连上"（DNS 慢、网络断、CORS 挂） |

**这是三个层次的保险**，本项目选了最贴近客户端的那一层。
**代价**：被掐断时抛的是 `AbortError`，必须**单独识别**，否则会和"网络不通"混为一谈 —— 这两种失败的排查方向完全相反。

### 4.3 手动判断 `res.ok`

| | |
|---|---|
| **关键事实** | `fetch` **只在"连通信都没建立"时 reject**。后端返回 400 / 500 时，它照样 resolve，只是 `res.status` 不是 2xx |
| **不判断的后果** | 把后端的 `{"error":"消息不能为空"}` 当正常回包解析，最后 `data.reply` 是 `undefined`，界面显示空白 —— 完全查不出原因 |
| **对标** | C# 里 `HttpClient` 也是同样设计，必须自己看 `IsSuccessStatusCode`。WPF 前作技术债 #4「`dynamic` 解析、不看状态码」就是死在这 |

### 4.4 两次 `await` —— 不是啰嗦，是协议分两段

```js
const res = await fetch(...)   // ① 等响应头
const data = await res.json()  // ② 等响应体
```

HTTP 响应本来就是"头先到、体后到"。`fetch` resolve 的那一刻，你只拿到了状态码和响应头，body 可能还在路上。
所以第一次 await 给你的是"能不能读"，第二次才是"内容是什么"。

**好处**：可以在读完头之后、读体之前做决定（比如看到 `res.ok` 为 false 就直接放弃读体，省流量）。
本项目没用上这个能力，但协议给你留了这个位置。

### 4.5 `finally` 里 `clearTimeout`

| | |
|---|---|
| **不清的后果** | 15 秒后闹钟照样响，对一个早就结束的请求调 `abort()`（无害但浪费）；定时器还持有 `controller` 引用，延迟回收 |
| **为什么放 finally** | 成功、失败、抛错三条路都会走到 finally。写在 try 末尾会漏掉失败路径，写在 catch 里会漏掉成功路径 |

## 五、配置层：四个决定，都在防"两处各算"

### 5.1 `localStorage` 而不是写死常量 / cookie / 后端配置

| 方案 | 问题 |
|---|---|
| 写死在 JS 里 | 换个地址要改代码 + 重启 dev server，没法给用户改 |
| cookie | 每次请求自动带上（浪费流量），前端读还得自己解析字符串 |
| 存在后端 | **鸡生蛋**：要知道后端地址才能去后端读配置 |
| `localStorage` | ✅ 同源持久、同步 API（不用 await）、5MB 够用、刷新还在 |

**代价**：只在这台机器的这个浏览器生效；隐私模式下可能直接抛异常（没包 try/catch）；不能跨设备。
V1 阶段这些都不重要，等有用户系统了再挪到后端。

### 5.2 `getApiBase()` 单一来源

```js
function getApiBase() {
  return normalizeBase(apiBaseInput.value) || API_DEFAULT
}
```

发消息和"测试连接"都调它。**如果两处各算一次**，最容易出现的 bug 是：用户改了地址，测试连通了，
但发消息用的是旧地址 —— 而两边代码看起来都"没写错"。这类 bug 的排查成本极高，因为它不报错。

### 5.3 `normalizeBase` 用正则

```js
raw.trim().replace(/\/+$/, '')
```

- `\/+` = 一个或多个斜杠
- `$` = 锚定结尾
- 合起来 = **把结尾所有斜杠一次干掉**（`http://a///` → `http://a`）

手动 `if (s.endsWith('/')) s = s.slice(0,-1)` 只能去一个，得套循环。
**代价**：只处理尾部。协议缺失、中间多余斜杠都不管 —— 这也是 06 里那个"漏了 `http://` 就误诊为连不上"的根源。

### 5.4 `classList.toggle(cls, force)` 的第二参数

```js
apiStatus.classList.toggle('pet__api-status--ok', ok === true)
apiStatus.classList.toggle('pet__api-status--err', ok === false)
```

| | |
|---|---|
| **替代** | `if (ok) { add('--ok'); remove('--err') } else { … }` 五行 |
| **好处** | 一行；而且**不可能出现两个类同时存在**的中间态（if/else 写错一个分支就会） |
| **为什么传 `ok === true`** | 调用时会传 `null`（连接中）。`null === true` 是 `false`、`null === false` 也是 `false` → 两个颜色类都被摘掉 → 回到默认灰。**用 `===` 而不是直接传 `ok`，是为了让"只有明确 true 才绿"这件事写在代码里** |

## 六、横向对比总表（核心）

| # | 用了什么 | 最常见的替代 | 主要好处 | 主要代价 / 边界 |
|---|---|---|---|---|
| 1 | 原生 DOM 操作 | React / Vue | 练 JS；所见即所得，好调试 | 视图与状态靠手同步 → 06 的 bug 就是证据 |
| 2 | `type="module"` | IIFE / 全局变量 | 自动 defer、不污染 window、可 import | 必须走 http |
| 3 | 节点存成常量 | 随用随查 | 只查一次；id 打错立刻暴露 | 节点被重建后引用失效 |
| 4 | `textContent` | `innerHTML` | 天然防 XSS；更快 | 不能塞富文本 |
| 5 | 单一渲染出口 | 各处自己拼 DOM | 改一处生效所有 | 参数成隐式协议，无类型保护 |
| 6 | `return li` 就地替换 | 删了再加 | 少一次重排；滚动不跳 | 调用方要持有引用 |
| 7 | `classList` | `style.display` / `className +=` | 幂等、不误伤别的类 | `.hidden` 得靠 `!important` 压组件 |
| 8 | 乐观更新 + 占位 | 等回来再显示 | 感知延迟≈0；失败可原地显示 | **必须兜住等待期间所有异步事件** |
| 9 | `isSending` + `disabled` | 只用一种 | 点击和回车两条路都堵 | 状态存两份（靠单一写入口保证同步） |
| 10 | `async/await` | `.then` 链 | 错误就地捕获；和 C# 一致 | 回调里用必须自带 catch |
| 11 | `AbortController` | `Promise.race` | **真的断开连接** | 要单独识别 `AbortError` |
| 12 | 手动 `res.ok` | 直接 `res.json()` | 4xx/5xx 不会当成功 | 要自己定义"什么算错" |
| 13 | 两次 `await` | —— | 协议本就分两段 | 容易漏第二个 |
| 14 | `finally` 清定时器 | try 末尾清 | 三条路径全覆盖 | —— |
| 15 | 存 timer ID + 先清 | 直接 setTimeout | 可重置，不会叠 | —— |
| 16 | `localStorage` | 写死 / cookie / 后端 | 不改代码就能换地址 | 只在本机本浏览器生效 |
| 17 | `getApiBase()` 单一来源 | 两处各算 | 不可能出现"一处生效一处不生效" | 多一层函数调用 |
| 18 | 正则去尾斜杠 | 手动判断 | 一次干掉所有尾斜杠 | 只管尾部 |
| 19 | `toggle(cls, force)` | if/else | 一行、无中间态 | —— |
| 20 | 三元判 `err.name` | 自定义错误子类 | 简单够用 | 错误类型一多就变字符串比较地狱 |
| 21 | 传函数名而非箭头 | `() => send()` | 可 `removeEventListener` | 拿不到 event |
| 22 | `console.error` | `alert` / 静默 | 不打断；线索不丢 | 用户看不见（开发期够用） |
| 23 | `trim()` 前置 | 不管 | 挡住空格消息 | 只是体验，防线在后端 |
| 24 | `isComposing` | 不判断 | 中文选词不会误发 | 只挡"组合中"，回车确认那下仍可能漏 |

## 七、三个"选对了、但代价已经出现"的地方

这三处最能说明**技术选型不是对错题，是取舍**。

### ① 乐观更新选了，但"对账"只做了一半

- 选对了：不这么写，用户每次都要等 2 秒才看到自己说的话。
- 代价出现了：等待期间那个 10 秒自动隐藏能把气泡藏掉，而回来只改文字不叫醒它。
- **结论**：乐观更新的完整成本 = 占位 + 兜住等待期间所有异步事件 + 失败回滚。这里只做了第一件。

### ② 不上框架选了，视图同步就得自己盯

- 选对了：练到了 DOM 操作、事件、异步，全是最核心的 JS。
- 代价出现了：`bubble` 的显隐、`inputBox` 的禁用、`pending` 的文字，三处状态散在三个地方，任何一处忘了改就出一个 bug（06 里 4 个问题里有 3 个是这类）。
- **结论**：这就是将来学框架最真实的动机。**先亲手被折腾过，框架才不是魔法。**

### ③ 字符串拼类名 `'pet__msg--' + from`

- 选对了：一行搞定，够用。
- 代价出现了：传错 `from` 不会报错，只会静默丢样式。
- **结论**：纯 JS 没有类型检查，"拼字符串"是最容易静默失败的地方。等上 TypeScript，这里会立刻变成编译错误。

## 八、总结

一句话：**这份代码的每一个"多写的几行"，都在补一个默认行为的坑。**

- `fetch` 默认不超时 → 多写 `AbortController`
- `fetch` 默认不判 4xx → 多写 `res.ok`
- `fetch` 默认不清理 → 多写 `finally`
- `setTimeout` 默认会叠加 → 多写 `clearTimeout`
- `innerHTML` 默认执行标签 → 改用 `textContent`
- 两处各算地址默认不报错 → 抽成 `getApiBase`

而它省掉的每一处，都是**明确判断过此刻不需要**的：不缓存/不虚拟 DOM、不上框架、不做类型、不做全局状态管理。

**判断标准其实就一条**：这个"坑"现在会不会真的发生？会 → 补；不会且补起来贵 → 记进 `record`，等它真的发生时再补。
