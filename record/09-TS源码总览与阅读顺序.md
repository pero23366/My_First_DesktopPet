## 〇、为什么不按文件名顺序读

按字母读会很难受：`api.ts` 一开始就 `import { ChatMessage } from './types'`，而你还没见过 `ChatMessage` 是什么；
`main.ts` 里全是 `initChat()` / `initSettings()`，而这两个函数你一个都还没读。

模块化代码有天然的**依赖方向**：被依赖的必须先读。这份项目里依赖是严格单向的（`main.ts` 头部自己写了这条规则）：

```
types.ts  ──┐
config.ts ──┤
            ├──→ persona.ts ──→ store.ts ──┐
            ├──→ ui.ts ───────────────────┼──→ chat.ts ──┐
            └──→ api.ts ─────────────────┼              ├──→ settings.ts ──→ main.ts
                                          └──────────────┘
```

读的方向就是箭头的反方向：**从没有任何依赖的文件开始，一路读到最顶上的装配层。**

## 二、逐篇讲解

### 1. `types.ts` — 名词表（42 行）

**职责**：只声明类型，不写任何值、任何逻辑。整个文件编译后**完全消失**。

**五组名词：**

```ts
export type ChatRole = 'system' | 'user' | 'assistant'
export interface ChatMessage { role: ChatRole; content: string }
```

- `ChatRole` 是**字面量联合类型**：只能是这三个字符串之一。写 `role: 'bot'` 立刻报错。
- 注释里那句"只有 OpenAI 协议里的三种 role，界面上的 me/pet 不属于这一层"很关键 —— 这是**两个不同世界的词**。

```ts
export type BubbleFrom = 'me' | 'pet'
```

界面层的词，和 `ChatRole` 刻意分开。为什么不合并成一个？因为 `role: 'assistant'` 和 `from: 'pet'` 指的是两件事：
一个是要发给模型的协议字段，一个是要挂到 DOM 上的 CSS 修饰类。混在一起，将来改任何一个都会牵连另一个。

```ts
export interface PersonaOptions { personality: string; tone: string; address: string }
export interface Persona { name: string; options: PersonaOptions; prompt: string }
```

`Persona` 里同时存了 `options` 和 `prompt`，看起来冗余 —— 但这是刻意的：
`options` 供界面回填下拉框，`prompt` 是真正发给模型的文本（可手改）。两者不同步是**允许的状态**。

```ts
export interface PetConfigFile {
  format: string
  savedAt: string
  persona: Persona
  image: string | null   // 没换过形象时为 null
}
```

`string | null` 就是 TS 表达"可能没有"的标准写法。注意**用了 `null` 而不是 `undefined`** —— 因为要序列化成 JSON，
而 JSON 里没有 `undefined`（`JSON.stringify({a: undefined})` 会直接丢掉这个键）。

```ts
export type RequestFailureKind = 'auth' | 'balance' | 'rate' | 'timeout' | 'network' | 'http' | 'empty'
```

**这是整个项目最有价值的一个类型。** 它把"失败"从一句人话降级成七个机器可读的类别。
好处：`classifyStatus()` 负责产生它，`failureText()` 负责消费它，中间没有任何字符串匹配。

**TS 语法点**：`type` vs `interface`
- `interface` 用来描述**对象形状**，可以被 `extends` 合并
- `type` 可以给任何东西起名，包括联合类型（`'a' | 'b'`）——`interface` 做不到
- 本文件的分工：**对象用 interface，联合用 type**，是非常主流的约定

### 2. `config.ts` — 常量表（45 行）

**职责**：所有"魔法数字"和"魔法字符串"的**唯一来源**，别的文件只准引用，不准自己写。

**分三类：**

| 类别 | 例子 | 为什么集中 |
|---|---|---|
| 接口地址 | `LLM_BASE_URL`、`LLM_CHAT_PATH` | 换供应商只改一处 |
| 存储键名 | `KEY_STORAGE = 'pet.apiKey'` | 键名拼错不会报错，只会静默读到空值 |
| 调参数字 | `MAX_TOKENS`、`HISTORY_TURNS`、`CHAT_TIMEOUT_MS` | 手感调整不必翻遍全项目 |

**最值得看的是这两行的对比：**

```ts
export const KEY_STORAGE = 'pet.apiKey'   // → sessionStorage
export const MODEL_STORAGE = 'pet.model'  // → localStorage
```

注释写得很清楚：Key 用 `sessionStorage`（刷新还在、关标签页即焚），模型名不是秘密所以放 `localStorage`。
**同一个项目里，两份数据用了两种存储，理由是"泄露面大小不同"。** 这是安全判断，不是随手写的。

`IMAGE_MAX_BYTES = 8 * 1024 * 1024` 这种写法（而不是 `8388608`）也是惯例：**让读的人一眼看出是 8MB。**

**TS 语法点**：`export const X = ...` 之后，TS 会自动把 `X` 的类型推断成**字面量**（`'https://api.deepseek.com'`），
不是 `string`。所以你在别处不能用别的字符串赋值给它 —— 但它本来也不该被赋值。

### 3. `persona.ts` — 人设（68 行）

**职责**：三件事，全都是纯函数/纯数据：给出可选项、把选项拼成提示词、给默认人设。**不碰 DOM、不发请求。**

**① 选项用数据描述，不用代码描述**

```ts
export const PERSONA_GROUPS = [
  { key: 'personality' as const, label: '性格', options: ['温柔', '有点丧', '活泼', '嘴毒', '冷静'] },
  { key: 'tone' as const, label: '语气', options: ['短句', '爱用省略号', '话多一点', '偶尔撒娇'] },
  { key: 'address' as const, label: '怎么称呼你', options: ['你', '主人', '同学', '朋友'] },
] satisfies ReadonlyArray<{
  key: keyof PersonaOptions
  label: string
  options: readonly string[]
}>
```

这段有个值得停下来的地方 —— **`satisfies` 运算符**：

| 写法 | 结果 |
|---|---|
| `const x: SomeType = [...]` | 类型被**强制变成** `SomeType`，原始字面量信息丢失 |
| `const x = [...] satisfies SomeType` | **检查**是否符合 `SomeType`，但保留原始推断（比如 `'性格'` 仍是字面量） |

为什么这里非要用 `satisfies`？因为后面 `settings.ts` 要写 `PERSONA_GROUPS.find(g => g.key === key)`，
如果类型被拓宽成 `{key: keyof PersonaOptions}`，`g.key` 就失去了"具体是哪一个"的信息。

`as const` 的作用是让 `key: 'personality'` 保持字面量，而不是被推断成 `string`。
如果没有 `as const`，`key` 就是 `string`，`satisfies` 那关反而过得去，但比对时会失去精确性。

**② 拼提示词**

```ts
export function buildPrompt(name: string, options: PersonaOptions): string {
  const who = name.trim() || '小沃'
  return [ `你叫「${who}」…`, `你的性格：${options.personality}…`, … ].join('\n')
}
```

- 返回**一段纯文本**，这是最终要作为 `role: 'system'` 发出去的东西
- 用数组 `.join('\n')` 而不是 `+` 拼接：每行独立，方便增删，也不会漏掉换行
- 规则那 6 条是**产品设计**不是技术：限制 40 字、不许说自己是 AI、不许用 Markdown…… 这些直接决定了桌宠像不像活物

**③ 为什么存 `prompt` 而不是只存 `options`**

注释里写了答案：导出给桌面版时，桌面端读到的是**拼好的文本**，不依赖网页这边的拼装规则。
**将来你改了 `buildPrompt`，已经导出的旧配置文件不会被影响。** 这是"数据要带版本语义"的思路。

**TS 语法点**：`options: PersonaOptions` 出现在参数位置，是"这个参数必须长得像 PersonaOptions"。
传 `{personality:'温柔'}` 少一个字段，编译期就报错 —— 这就是 TS 在替你做的那件事。

### 4. `store.ts` — 运行时状态（41 行）

**职责**：存"当前生效的值"。`settings` 往里写，`chat` 往外读，**两边谁都不用认识谁**。

```ts
export const store = {
  apiKey: sessionStorage.getItem(KEY_STORAGE) ?? '',
  model: localStorage.getItem(MODEL_STORAGE) ?? LLM_MODEL_DEFAULT,
  persona: defaultPersona() as Persona,
  imageDataUrl: null as string | null,
}
```

四个细节：

| 写法 | 为什么这么写 |
|---|---|
| `?? ''` 而不是 `\|\| ''` | `??` 只在 `null / undefined` 时兜底；`\|\|` 会把空字符串也当成假值。这里结果一样，但语义更准 |
| `?? LLM_MODEL_DEFAULT` | 第一次运行 localStorage 是空的，必须给默认模型 |
| `defaultPersona() as Persona` | 其实是**多余的断言**（函数本来就返回 Persona），可以删 |
| `null as string \|\| null` | 这个必须有：对象字面量里的 `null` 会被推断成 `null` 类型，之后 `store.imageDataUrl = dataUrl` 就报错。断言成 `string \| null` 才能重新赋值 |

**三个写入函数，都有明确的语义：**

```ts
export function saveKey(raw: string): void {
  const key = raw.trim()
  store.apiKey = key
  if (key) sessionStorage.setItem(KEY_STORAGE, key)
  else sessionStorage.removeItem(KEY_STORAGE)   // 传空 = 清除
}
```

- **内存和存储同时改**，不允许只改一份（否则刷新页面行为就不一致）
- 传空字符串 → `removeItem`：用一个函数同时表达"设置"和"清除"

`saveModel` 里 `raw.trim() || LLM_MODEL_DEFAULT`：用户清空模型名 → 自动回到默认，而不是存一个空字符串。

**架构上的价值**：`store` 是**唯一**存放可变状态的地方。`chat.ts` 里没有任何模块级状态（除了 `history` 和 `isSending`），
`settings.ts` 也不存值。**状态集中 = 排查问题时只用看一个文件。**

### 5. `ui.ts` — 视图层（172 行）

**职责**：唯一碰 DOM 的地方。提供"改界面"的小函数，**不发请求、不做决策**。

**① `must()` —— 类型安全的 querySelector**

```ts
function must<T extends Element>(selector: string): T {
  const el = document.querySelector<T>(selector)
  if (!el) throw new Error(`找不到元素：${selector}`)
  return el
}
```

这是本文件最重要的 5 行。对比三种写法：

| 写法 | 问题 |
|---|---|
| `document.querySelector('#x')` | 返回 `Element \| null`，后面每次用都要判空 |
| `document.querySelector('#x')!` | 用 `!` 强行告诉 TS"它一定存在"，**错了也是运行时才发现** |
| `must('#x')` | 找不到就**立刻抛错，并且报出是哪个选择器** |

**代价要说清楚**：`dom` 对象在**模块加载时**就执行了全部 23 次 `must()`。任何一个 id 打错，
整个模块加载就崩，页面全白。这是"尽早失败"——好处是一眼能定位，坏处是一个错拖垮全站。

**② 23 个节点一次抓完**

```ts
export const dom = {
  home: must<HTMLElement>('#home'),
  chatLog: must<HTMLUListElement>('#chatLog'),
  inputBox: must<HTMLInputElement>('#inputBox'),
  ...
}
```

`<T>` 里的泛型决定了两件事：① 返回值的类型；② **能用哪些属性**。
`HTMLInputElement` 才有 `.value`，`HTMLElement` 没有 —— 这就是为什么 `inputBox` 必须标成 `HTMLInputElement`。

**③ 消息渲染**

```ts
export function addMessage(text: string, from: BubbleFrom): HTMLLIElement {
  const li = document.createElement('li')
  li.className = `pet__msg pet__msg--${from}`
  li.textContent = text            // 不用 innerHTML：用户输入不会被当成标签
  dom.chatLog.append(li)
  dom.bubble.classList.remove('hidden')
  dom.chatLog.scrollTop = dom.chatLog.scrollHeight
  return li
}
```

`return li` 是给"占位替换"用的：`chat.ts` 先放一个 `…`，收到回复后直接改这个 `li` 的文字。

**④ 自动隐藏：状态从 `chat.ts` 搬到了这里**

```ts
let hideTimer: number | null = null
let autoHideEnabled = true
```

`number` 是因为**浏览器环境**的 `setTimeout` 返回数字 id（Node 环境返回 `Timeout` 对象）。
这个模块有 `lib: ["DOM"]`，所以标 `number` 是对的。

`cancelAutoHide()` 里先判 `!== null` 再清 —— 比直接 `clearTimeout(null)` 更严谨，也顺手把 `hideTimer` 置回 `null`。

**⑤ 下载文件**

```ts
const blob = new Blob([JSON.stringify(data, null, 2)], { type: 'application/json' })
const url = URL.createObjectURL(blob)
const a = document.createElement('a')
a.href = url; a.download = filename; a.click()
URL.revokeObjectURL(url)   // 立刻回收
```

- `JSON.stringify(data, null, 2)` 的第三个参数 = 缩进 2 空格，导出的文件用记事本能看懂
- `URL.revokeObjectURL` 必须调，否则这份 Blob 一直占内存直到刷新
- 用 `<a download>` 而不是 `window.open`：不依赖后端、不会被弹窗拦截

### 6. `api.ts` — 网络层（129 行）

**职责**：唯一和网络打交道的地方。**不碰 DOM、不拼人设、不说人话**，只把结果或失败原因交回去。

**① 返回值设计 —— 不抛异常**

```ts
export type ChatOutcome =
  | { ok: true; content: string }
  | { ok: false; failure: ChatFailure }
```

这是**可辨识联合**（discriminated union）。调用方这样用：

```ts
const result = await requestCompletion(messages, {...})
if (result.ok) {
  result.content   // ← TS 知道你在这个分支里一定能拿到 content
} else {
  result.failure   // ← 这里才知道有 failure
}
```

对比"抛异常"：异常的类型在签名上是看不见的（`catch (e)` 里 `e` 是 `unknown`），
而这种写法把"可能失败"写进了**函数签名**，调用方不处理编译器就报错。**这是 TS 最值钱的用法之一。**

**② 失败分类**

```ts
function classifyStatus(status: number): RequestFailureKind {
  if (status === 401 || status === 403) return 'auth'
  if (status === 402) return 'balance'
  if (status === 429) return 'rate'
  return 'http'
}
```

**这一层只做事实分类，不做措辞。** 用户看到的"Key 好像不对"是 `chat.ts` 翻译的 —— 界面文案归业务层，
网络层只说"auth"。这样将来做多语言、或者换成状态栏提示，都不用动这一层。

**③ 三个必须自己补的 `fetch` 坑**

| 坑 | 代码 |
|---|---|
| 不超时 | `AbortController` + `setTimeout(abort, timeout)` |
| 不为 4xx/5xx reject | `if (!res.ok) { ... }` |
| 不清定时器 | `finally { clearTimeout(timer) }` |

`AbortError` 的判断写成了 `err instanceof DOMException && err.name === 'AbortError'` ——
比只判 `err.name` 更稳，因为先确认它是 DOM 的异常对象。

**④ 防御性解析**

```ts
const data = (await res.json()) as CompletionResponse
const content = data.choices?.[0]?.message?.content?.trim() ?? ''
if (!content) return { ok: false, failure: { kind: 'empty' } }
```

`?.` 可选链一路挂到底：任何一层缺字段都不会崩，最后落到 `''`，再转成 `empty` 失败。
对比 WPF 前作用 `dynamic` 解析、结构一变就崩 —— 这是技术债 #4 的正式修复。

**⑤ `testKey` 的一个巧妙处理**

```ts
if (!result.ok && result.failure.kind === 'empty') return { ok: true }
```

因为测试用的是 `max_tokens: 1`，模型可能只回一个字符甚至 0 个 token，`content` 为空是**正常的**。
只要没报错就算 Key 有效。这个细节不写注释的话，后人一定会当成 bug 删掉。

### 7. `chat.ts` — 对话业务（103 行）

**职责**：完整跑一遍"读输入 → 上屏 → 拼 messages → 请求 → 回填 → 解锁"。三次依赖都在这一层汇合。

**① `send()` 的顺序是有讲究的**

```ts
const text = ui.readInput()
if (text === '') return
if (isSending) return

ui.addMessage(text, 'me')     // ① 自己先上屏
ui.clearInput()               // ② 清空输入框
ui.scheduleAutoHide()         // ③ 开始计时

if (!store.apiKey) {          // ④ 没 Key 就别白跑一次请求
  ui.addMessage('（我还没拿到说话的能力…）', 'pet')
  ui.dom.settingsPanel.classList.remove('hidden')
  return
}

const pending = ui.addMessage('…', 'pet')   // ⑤ 占位
setSending(true)
```

第 ④ 步值得注意：**没填 Key 时不是报错，而是把用户直接送到设置面板**。
（`ui.dom.settingsPanel` 在这里被直接操作 —— 严格说这算 `chat` 越过了 `ui` 的封装，是个小瑕疵。）

**② messages 怎么拼**

```ts
const messages: ChatMessage[] = [
  { role: 'system', content: store.persona.prompt },   // 人设，每次一条
  ...history.slice(-HISTORY_TURNS * 2),                // 最近 6 轮 = 12 条
  { role: 'user', content: text },                     // 这一句
]
```

- `system` 只放最前面一条，**不进 history** —— 它每次都重新拼，不占历史额度
- `HISTORY_TURNS * 2`：一轮 = user + assistant 两条
- `slice(-n)` 取末尾 n 条。负数索引从尾部算

**③ 历史只在成功时记录**

```ts
if (result.ok) {
  pending.textContent = result.content
  history.push({ role: 'user', content: text })
  history.push({ role: 'assistant', content: result.content })
} else {
  pending.textContent = failureText(result.failure)
}
```

注释写得很准：**失败的占位文案不该被模型当成自己说过的话。**
如果失败也 push，下一轮模型会看到自己说过"（Key 好像不对）"，人设就崩了。

而且 `push` 是**成对**的两行 —— 这正是 WPF 前作技术债 #2（`RemoveAt(1)` 粗暴截断可能删掉 user 只留 assistant，导致 API 400）的修复思路：
**user 和 assistant 永远同进同出。**

**④ 错误翻译在这一层**

```ts
function failureText(failure: ChatFailure): string {
  switch (failure.kind) {
    case 'auth': return '（Key 好像不对，去设置里看一下）'
    ...
  }
}
```

`switch` 覆盖了 7 个 kind 中的 6 个，最后的 `default` 兜底 `http`。
TS 能检查这个 switch 是否穷尽 —— 如果把 `default` 删掉，并给函数标 `: string`，漏一个 case 会报错。

**⑤ `void send()`**

```ts
if (event.key === 'Enter') void send()
```

`send` 是 `async`，返回 `Promise<void>`。事件的第二个参数（`keydown` 的第三个参数）要求传 `void` 返回的回调。
`void` 前缀是**显式声明"我故意不接这个 Promise"**，比直接写 `send()` 更能表达意图，也躲开 lint 的 `no-floating-promises`。

### 8. `settings.ts` — 设置业务（219 行，最长）

**职责**：四块功能拼在一起 —— API 配置、人设编辑、形象上传、其他（自动隐藏/清空/导出）。

结构很清晰：`initSettings()` 一次调四个 `initXxxSection()`，每块自己绑定自己的事件。

**① 边输边存**

```ts
ui.dom.apiKey.addEventListener('input', () => saveKey(ui.dom.apiKey.value))
ui.dom.apiModel.addEventListener('change', () => saveModel(ui.dom.apiModel.value))
```

注意两个事件不同：`input`（每敲一个字）vs `change`（失焦或回车才触发）。
Key 用 `input` 是为了"粘上去立刻生效"，模型名用 `change` 是因为它是下拉/短文本，没必要每个字符都写盘。

**② 下拉框由数据生成**

```ts
function fillSelect(select: HTMLSelectElement, key: keyof PersonaOptions): void {
  const group = PERSONA_GROUPS.find((g) => g.key === key)
  if (!group) return
  ...
}
```

`keyof PersonaOptions` = `'personality' | 'tone' | 'address'`。传别的字符串，编译期就报错。
**这就是为什么 `persona.ts` 里要用 `satisfies` 保留字面量** —— 不然 `g.key === key` 这里的比对会退化。

**③ 一个刻意的"不贴心"**

```ts
// 注意：这里故意不监听 change 自动重拼提示词。
// 用户可能已经手改过提示词，改个下拉就把它冲掉，是最让人恼火的一种"贴心"。
```

这段注释是全项目最值得学的一句。**技术上能自动同步，但产品上不该自动同步。**
用户手改过的文本是"他的作品"，改下拉框只是"换个生成起点"，不能覆盖作品。想覆盖就点「生成提示词」。

**④ 人设的三份数据谁是老大**

| 数据 | 存在哪 | 谁是权威 |
|---|---|---|
| 下拉框的值 | DOM | 只是"生成提示词的输入" |
| `store.persona.options` | store | 记录上次选了什么 |
| `store.persona.prompt` | store | **最终事实**，发出去的是它 |

所以手改 textarea 时直接改 `prompt`，改下拉框**不**动 `prompt` —— 只在点按钮时才重算。

**⑤ 形象上传**

```ts
const reader = new FileReader()
reader.onload = () => {
  const dataUrl = String(reader.result)
  store.imageDataUrl = dataUrl
  ui.setPetImage(dataUrl)
}
reader.readAsDataURL(file)
```

注释给了关键理由：**用 data URL 而不是 ObjectURL，因为导出配置时要把图内嵌进 JSON**，
ObjectURL 一出页面就失效，写不进文件。这是"两个需求（显示 + 导出）同时满足"的唯一选择。

三道校验顺序也对：先 `file.type` 再 `file.size`，都不通过才不进 Reader。

**⑥ 导出**

```ts
const safeName = file.persona.name.replace(/[\\/:*?"<>|]/g, '_')
ui.downloadJson(`${safeName}.pet.json`, file)
```

Windows 文件名不允许 `\ / : * ? " < > |`，用正则统统换成 `_`。
不处理的话，名字里带个 `/` 浏览器会静默改成别的，用户找不到文件。

注意 `prompt` 取的是 `ui.dom.personaPrompt.value`（界面上的值）而不是 `store.persona.prompt` ——
**以用户看到的为准**，这个选择是对的。

### 9. `main.ts` — 装配入口（37 行）

**职责**：只做两件事 —— 按顺序调 init、绑定最外层的两个按钮。

```ts
ensurePersona()
initSettings()
initChat()
```

**顺序的理由，注释写得很清楚：**

| 顺序 | 为什么 |
|---|---|
| 1. `ensurePersona()` | 人设先有默认值，settings 才能把它灌进表单 |
| 2. `initSettings()` | 先把表单值和 store 对齐，再让用户能改 |
| 3. `initChat()` | 最后绑发送事件，确保点击时读到的是初始化过的 store |

如果一个 id 写错了，`ui.ts` 的 `must()` 会在 import 阶段就抛错 —— 你的控制台会直接告诉你哪个选择器找不到。
**这就是"依赖是单向的、加载有顺序"带来的可调试性。**

剩下的就是两个按钮：

```ts
ui.dom.createPetBtn.addEventListener('click', () => {
  ui.showPet()
  if (ui.dom.chatLog.children.length === 0) ui.addMessage('我在这儿。想聊点什么？', 'pet')
  ui.focusInput()
})
```

`children.length === 0` 保证欢迎语只在第一次出现 —— 来回切换视图不刷屏。

## 三、散落在各文件的 TS 语法点索引

| 语法 | 出现位置 | 一句话 |
|---|---|---|
| 字面量联合类型 | `types.ts` `ChatRole` | 只能是列出的那几个字符串 |
| `type` vs `interface` | `types.ts` | 对象用 interface，联合用 type |
| `string \| null` | `types.ts` `PetConfigFile.image` | 表达"可能没有"，用 null 而不是 undefined（JSON 里 undefined 会消失） |
| `??` 空值合并 | `store.ts` | 只在 null/undefined 时兜底，空字符串不算 |
| `?.` 可选链 | `api.ts` | 一路挂到底，中间缺字段不崩 |
| `as` 类型断言 | `store.ts` / `api.ts` | 告诉编译器"我知道它是什么"，风险自负 |
| 泛型函数 `<T extends Element>` | `ui.ts` `must` | 约束 + 保留返回类型 |
| `querySelector<T>` | `ui.ts` | 泛型决定返回类型和可用属性 |
| `keyof` | `settings.ts` `fillSelect` | 取一个 interface 的所有键名组成的联合 |
| `satisfies` | `persona.ts` `PERSONA_GROUPS` | 检查形状但保留字面量推断 |
| `as const` | `persona.ts` | 把 `'性格'` 钉成字面量而不是 `string` |
| `readonly string[]` | `persona.ts` | 声明不会改这个数组 |
| 可辨识联合 | `api.ts` `ChatOutcome` | 靠 `ok` 字段收窄，把"可能失败"写进签名 |
| 联合类型收窄 | `chat.ts` `if (result.ok)` | 同一个变量在两个分支里是不同的类型 |
| `import type` | 多数文件 | 只导类型，编译后整行消失 |
| `import * as ui` | `chat/settings/main` | 命名空间导入，调用处写 `ui.xxx` 一眼看出是视图层 |
| `void promise` | `chat.ts` / `settings.ts` | 显式声明"这个 Promise 我故意不接" |
| `Promise<void>` 返回值 | `send()` | 异步函数没返回值时写 `void` |
| 对象展开 | `settings.ts` | `{ ...store.persona, name }` 复制并覆盖一个字段 |
| `Array.prototype.slice` 负索引 | `chat.ts` | 从尾部取 N 个 |
| `window.setTimeout` → `number` | `ui.ts` | 浏览器环境返回数字 id（Node 环境是对象） |

## 四、架构上的三条规矩

1. **依赖单向，`main.ts` 在最上层**
   没有任何模块 import `main`。`main` 只 import 别人。这条守住了，就不会出现循环依赖。

2. **每一层只干一件事**
   - `api` 只说事实（`auth` / `timeout`），不说人话
   - `ui` 只碰 DOM，不发请求、不做判断
   - `store` 只存值，不判断
   - `chat` / `settings` 才是做决定的地方
   
   证据：**同一个概念在两层各有一份翻译**（`chat.ts` 的 `failureText` 和 `settings.ts` 的 `failureText`）。
   看起来重复，其实是"气泡里说什么"和"设置面板状态行说什么"——措辞本来就该不同。

3. **状态集中，只有一个 `store`**
   模块级变量只有三处：`chat.ts` 的 `history` / `isSending`，`ui.ts` 的 `hideTimer` / `autoHideEnabled`。
   其余全部在 `store` 里。排查"为什么页面显示的值不对"时，只用看这一个文件。

## 五、读的时候发现的问题

### ① 回复慢于 10 秒时，回复可能看不见（竞态仍在）

```ts
ui.scheduleAutoHide()          // 第 39 行：一发送就开始 10 秒倒计时
...
const result = await requestCompletion(...)   // 最长 30 秒
pending.textContent = result.content          // 只改文字，没叫醒气泡
```

如果请求耗时超过 10 秒：气泡在 10 秒时被加上 `.hidden`，回复到达时只改了 `textContent`，**气泡仍然是隐藏的**。

**最干净的修法**：把第 39 行的 `ui.scheduleAutoHide()` 删掉。
因为第 76 行（请求结束后）本来就会调一次，那一处才是正确的计时起点。
发送瞬间就开始倒计时，本身就是错的语义。

### ② `ensurePersona()` 永远不会执行内部逻辑

```ts
export function ensurePersona(): void {
  if (!store.persona.prompt) savePersona(defaultPersona())
}
```

而 `store.ts` 里 `persona: defaultPersona() as Persona` —— `prompt` 一出生就是非空字符串。
所以这个 `if` 永远为假。**它是死代码**（除非将来 store 改成从外部载入）。

### ③ `store.ts` 的 `as Persona` 是多余断言

`defaultPersona()` 的返回类型本来就是 `Persona`，不需要 `as`。删掉不会报错。
（`imageDataUrl` 那个 `as string | null` 是**必需的**，别一起删。）

### ④ `chat.ts` 直接操作了 `ui.dom.settingsPanel`

```ts
ui.dom.settingsPanel.classList.remove('hidden')
```

`dom` 是导出的，所以能这么写，但它绕过了 `ui` 提供的函数。更一致的做法是在 `ui.ts` 加一个 `openSettings()`。

## 六、总结：这份 TS 代码真正教了什么

1. **类型不是装饰，是设计工具。** `RequestFailureKind` 那 7 个字面量，直接把"失败"从一个模糊概念变成了可穷尽检查的集合。
2. **`fetch` 的三个默认坑必须自己补**（超时、4xx 不 reject、定时器不清），`api.ts` 里三样全都补了。
3. **返回 `{ok, ...}` 比抛异常更适合前端**：把"可能失败"写进签名，调用方漏处理编译器就报错。
4. **`satisfies` + `as const` 这一对**，是"既要检查、又要保住精确类型"的唯一写法，`persona.ts` 里那 30 行值得反复看。
5. **注释里写的"为什么"，比代码本身更值钱。** 比如"故意不自动重拼提示词"、"故意不用 ObjectURL"、"存 prompt 不存 options" —— 这三处都是产品判断，不是技术判断。
